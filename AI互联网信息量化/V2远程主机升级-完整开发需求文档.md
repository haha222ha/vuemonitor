## 二、Notion设计逻辑吸收与优化

### 2.1 需要保留并迁移的核心设计

| 设计逻辑 | 来源 | 迁移方式 |
|---------|------|---------|
| **6数据库分类体系** | Notion Schema | 映射为PostgreSQL 6张表，保留所有字段 |
| **upsert同步策略** | notion_client_wrapper | 改为FastAPI POST/PUT接口，标题唯一键匹配 |
| **三级会员权限** | Notion页面筛选 | 改为JWT token + role字段 + API过滤，保留3产品体系(weekly/monthly/yearly)，新增free和enterprise |
| **Dashboard数据聚合** | Notion Linked View | 改为Vue.js组件 + FastAPI聚合查询接口 |
| **每周/月自动生成** | Notion页面模板 | 改为FastAPI定时任务 + PG存储 |
| **历史趋势回溯** | Notion数据库视图 | 改为PG时间序列查询 |
| **数据可视化** | Notion Gallery/Board/Calendar视图 | 改为Vue.js + ECharts/Chart.js |

### 2.2 需要优化改进的设计

| 原Notion设计的局限 | 优化方案 |
|-------------------|---------|
| 权限靠页面隔离+分享链接密码，安全性弱 | JWT + API Key + 授权码三级鉴权 |
| 无法做用户级权限（同一页面所有人看到相同内容） | PG行级权限 + 用户角色字段 |
| 同步有350ms间隔限流，大批量慢 | FastAPI批量写入接口 + 异步队列 |
| 无法做支付自动化 | 授权码激活机制：管理员发放授权码→用户激活→自动开通对应等级权限 |
| 依赖第三方(Notion/Super.so)稳定性 | 完全自控，无外部依赖 |
| 数据分析能力弱（Notion非专业数据库） | PG支持复杂SQL/聚合/时序分析 |
| 前端展示受限于Notion排版 | Vue.js自由定制UI/UX |

## 三、核心技术决策

### 3.1 情报系统展示方式：静态优先 — 构建时生成 + Nginx直出

**核心判断：情报站天然适合静态交付，数据离线生产→同步推送→前端只读消费。**

| 方案 | 定位 | 说明 |
|------|------|------|
| **静态生成 (Vue.js dist + JSON)** | 所有情报页面 | 同步后构建一次，Nginx直出，速度最快 |
| **FastAPI** | 仅鉴权接口 | 登录、授权码激活、JWT验证，不参与数据查询 |

**决策理由**：

```
为什么选择静态优先？
  - 数据一天更新一次，不是用户实时产生 → 无需动态API
  - 会员看到的数据是同步时确定的 → 预构建分级JSON即可
  - 搜索/筛选/排序 → 前端全量加载后客户端处理（数据量小，毫秒级）
  - Dashboard聚合数据 → 同步时预计算，写入dashboard.json
  - 报告 → 本身就是静态HTML/PDF，无需后端参与
  - Nginx直出 → 0ms后端耗时，上万并发无压力
  - FastAPI只做鉴权 → 95%请求命中Nginx静态文件

架构决策：
  静态文件 (Nginx直出，95%请求):
    ├── Vue.js SPA壳（index.html + JS/CSS）
    ├── 分级数据JSON（free/weekly/monthly/yearly/enterprise各一份）
    ├── Dashboard预计算数据（TOP10、环比变化）
    └── 报告HTML/PDF文件

  API (FastAPI，5%请求):
    ├── POST /api/auth/login          ← 登录获取JWT
    ├── POST /api/auth/activate-code   ← 授权码激活
    └── GET  /api/members/me           ← 验证JWT返回角色
```

### 3.2 技术栈确定

| 层级 | 技术 | 说明 |
|------|------|------|
| **前端** | Vue.js 3 + Vite + Pinia + Vue Router | SPA架构，组件化 |
| **UI框架** | Element Plus / Naive UI | 企业级组件库，Dashboard风格 |
| **图表** | ECharts 5 | 趋势曲线、评分雷达图、生命周期图 |
| **后端** | FastAPI (Python 3.10+) | 高性能异步API |
| **数据库** | PostgreSQL 15+ | 结构化趋势数据 |
| **缓存** | Redis | JWT黑名单、API限流、热点数据 |
| **部署** | Docker + Nginx + Uvicorn | 容器化部署 |
| **认证** | JWT + API Key + 授权码 | 三级鉴权体系 |

## 五、独立授权码体系设计

### 5.1 授权码核心模型

```
授权码 = 会员开通凭证 + 外部系统接入凭证（双用途）

授权码结构：
  AIOS-{会员等级}-{随机段}-{校验段}
  
  示例：
    AIOS-WEEKLY-a1b2c3d4e5f6-xyz1    ← 一周精选
    AIOS-MONTHLY-b2c3d4e5f6g7-abc2   ← 月度会员
    AIOS-YEARLY-c3d4e5f6g7h8-def3    ← 年度会员
    AIOS-ENT-d4e5f6g7h8i9-ghi4       ← 企业对接

生成规则：
  - 前缀：AIOS（固定标识）
  - 会员等级：WEEKLY/MONTHLY/YEARLY/ENT（对应会员产品）
  - 随机段：12位 base36 随机字符串
  - 校验段：前3段SHA256的前4位
```

**授权码与会员策略严格对应**：

授权码不是独立设计的，而是会员策略的执行载体。每个授权码必须绑定一个会员产品等级，激活后自动赋予对应权限和有效期。

### 5.2 授权码双用途设计

```
用途1：会员开通（面向C端用户）
  ┌──────────────────────────────────────────────────────────┐
  │ 管理员创建授权码 → 指定会员等级(weekly/monthly/yearly)    │
  │ → 系统自动设置有效期(7天/30天/365天)                       │
  │ → 用户激活后获得对应等级权限                                │
  └──────────────────────────────────────────────────────────┘

用途2：外部系统对接（面向B端企业）
  ┌──────────────────────────────────────────────────────────┐
  │ 管理员创建授权码 → 指定等级为enterprise                    │
  │ → 系统生成client_id + client_secret                       │
  │ → 外部系统通过HMAC签名调用API                              │
  │ → 权限范围和频率由授权码的permissions字段控制               │
  └──────────────────────────────────────────────────────────┘
```

### 5.3 授权码状态机

```
                    ┌──────────┐
          创建 ───→ │  active  │ ←── 正常使用
                    └────┬─────┘
                         │
              ┌──────────┼──────────┐
              ↓          ↓          ↓
         ┌────────┐ ┌────────┐ ┌──────────┐
         │frozen  │ │expired │ │revoked   │
         │(冻结)  │ │(过期)  │ │(吊销)    │
         └────────┘ └────────┘ └──────────┘
              │          │          │
              └──────────┼──────────┘
                         ↓
                    ┌──────────┐
                    │ deleted  │ ← 物理删除（30天后）
                    └──────────┘

状态流转：
  active → frozen    : 管理员手动冻结（临时禁用）
  active → revoked   : 管理员吊销（永久禁用，安全事件）
  active → expired   : 达到过期时间自动过期
  frozen → active    : 管理员解冻
  frozen → expired   : 冻结期间到期
  expired → deleted  : 过期30天后清理
  revoked → deleted  : 吊销30天后清理
```

### 5.4 授权码数据结构

```sql
-- auth_codes 表
CREATE TABLE auth_codes (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    code            VARCHAR(64) NOT NULL UNIQUE,           -- 授权码明文（仅创建时返回）
    code_hash       VARCHAR(256) NOT NULL UNIQUE,          -- SHA256哈希（用于验证）
    
    -- 会员策略绑定（核心：授权码由会员策略驱动）
    member_level    VARCHAR(20) NOT NULL,                  -- weekly/monthly/yearly/enterprise
    duration_days   INTEGER NOT NULL,                      -- 有效天数：7/30/365/-1(自定义)
    
    -- 关联信息
    client_name     VARCHAR(128) NOT NULL,                  -- 接入系统名称 / 用户昵称
    owner_email     VARCHAR(256),                           -- 负责人邮箱
    
    -- 企业对接专用（仅enterprise等级使用）
    client_id       VARCHAR(64),                            -- 客户端ID（enterprise必填）
    client_secret   VARCHAR(256),                           -- 客户端密钥（enterprise必填，HMAC-SHA256哈希存储）
    permissions     JSONB DEFAULT '[]',                     -- 允许的API端点列表（enterprise专用）
    rate_limit      INTEGER DEFAULT 100,                    -- 每小时请求限制（enterprise专用）
    
    -- 激活控制
    is_reusable     BOOLEAN NOT NULL DEFAULT FALSE,         -- 是否可复用（多人激活同一码）
    max_activations INTEGER,                                -- 最大激活次数（NULL=无限）
    current_activations INTEGER NOT NULL DEFAULT 0,         -- 已激活次数
    
    -- 生命周期
    status          VARCHAR(20) NOT NULL DEFAULT 'active',  -- active/frozen/expired/revoked
    created_at      TIMESTAMP NOT NULL DEFAULT NOW(),
    expires_at      TIMESTAMP,                              -- 授权码本身过期时间（区别于会员有效期）
    last_used_at    TIMESTAMP,                              -- 最后使用时间
    frozen_at       TIMESTAMP,                              -- 冻结时间
    revoked_at      TIMESTAMP,                              -- 吊销时间
    revoked_reason  TEXT,                                   -- 吊销原因
    
    -- 元数据
    metadata        JSONB DEFAULT '{}',                     -- 扩展元数据
    created_by      VARCHAR(128),                           -- 创建人
    
    -- 约束：enterprise等级必须有client_id和client_secret
    CONSTRAINT chk_enterprise_auth CHECK (
        member_level != 'enterprise' OR (client_id IS NOT NULL AND client_secret IS NOT NULL)
    )
);

-- auth_code_activations 表（激活记录，替代简单的计数器）
CREATE TABLE auth_code_activations (
    id              BIGSERIAL PRIMARY KEY,
    auth_code_id    UUID NOT NULL REFERENCES auth_codes(id),
    user_id         UUID NOT NULL REFERENCES members(id),   -- 激活的用户
    activated_level VARCHAR(20) NOT NULL,                   -- 激活时获得的等级
    activated_at    TIMESTAMP NOT NULL DEFAULT NOW(),       -- 激活时间
    expires_at      TIMESTAMP NOT NULL,                     -- 会员到期时间
    is_active       BOOLEAN NOT NULL DEFAULT TRUE,          -- 该次激活是否仍有效
    revoked_at      TIMESTAMP                              -- 撤销时间
);

-- auth_code_usage_logs 表（API调用日志，enterprise专用）
CREATE TABLE auth_code_usage_logs (
    id              BIGSERIAL PRIMARY KEY,
    auth_code_id    UUID NOT NULL REFERENCES auth_codes(id),
    endpoint        VARCHAR(256) NOT NULL,
    method          VARCHAR(10) NOT NULL,
    ip_address      INET,
    user_agent      TEXT,
    status_code     INTEGER,
    response_time_ms INTEGER,
    created_at      TIMESTAMP NOT NULL DEFAULT NOW()
);

CREATE INDEX idx_auth_codes_status ON auth_codes(status);
CREATE INDEX idx_auth_codes_code_hash ON auth_codes(code_hash);
CREATE INDEX idx_auth_codes_member_level ON auth_codes(member_level);
CREATE INDEX idx_auth_activations_user ON auth_code_activations(user_id);
CREATE INDEX idx_auth_activations_auth_code ON auth_code_activations(auth_code_id);
CREATE INDEX idx_auth_logs_created ON auth_code_usage_logs(created_at);
```

### 5.5 授权码鉴权流程

**场景A：C端用户激活授权码（weekly/monthly/yearly）**

```
用户在会员中心输入授权码：

Step 1: 用户提交授权码
  POST /api/v1/auth/activate
  Body: { "auth_code": "AIOS-MONTHLY-b2c3d4e5f6g7-abc2" }

Step 2: 服务端验证
  ┌──────────────────────────────────────────────────────┐
  │ 计算code_hash = SHA256(auth_code)                     │
  │ 查询auth_codes WHERE code_hash = ? AND status='active'│
  └──────────────┬───────────────────────────────────────┘
                 ↓ 找到记录
  ┌──────────────────────────────────────────────────────┐
  │ 检查激活限制                                          │
  │ current_activations < max_activations ?               │
  │ (或 is_reusable = TRUE 则跳过)                        │
  └──────────────┬───────────────────────────────────────┘
                 ↓ 可激活
  ┌──────────────────────────────────────────────────────┐
  │ 计算会员到期时间                                       │
  │ expires_at = NOW() + duration_days                    │
  │ (weekly=7天, monthly=30天, yearly=365天)               │
  └──────────────┬───────────────────────────────────────┘
                 ↓
  ┌──────────────────────────────────────────────────────┐
  │ 写入auth_code_activations表                           │
  │ 更新用户role = member_level                           │
  │ current_activations += 1                              │
  │ (一次性授权码: 激活后status→frozen)                    │
  └──────────────┬───────────────────────────────────────┘
                 ↓
  ┌──────────────────────────────────────────────────────┐
  │ 返回新JWT Token (role已升级)                           │
  │ { "status": "activated", "role": "monthly",           │
  │   "expires_at": "2026-06-23T00:00:00Z" }              │
  └──────────────────────────────────────────────────────┘
```

**场景B：B端企业API调用（enterprise）**

```
外部系统调用本系统API：

Step 1: 请求携带 Header
  X-API-Key: {client_id}:{signature}
  X-Timestamp: {unix_timestamp}

Step 2: 服务端验证
  ┌──────────────────────────────────────┐
  │ 请求进入 → 提取client_id + signature │
  └──────────────┬───────────────────────┘
                 ↓
  ┌──────────────────────────────────────┐
  │ 查询auth_codes表                     │
  │ WHERE client_id = ? AND status='active'│
  └──────────────┬───────────────────────┘
                 ↓ 找到记录
  ┌──────────────────────────────────────┐
  │ 验证签名                             │
  │ HMAC-SHA256(request_body, secret) == │
  │ signature ?                          │
  └──────────────┬───────────────────────┘
                 ↓ 签名有效
  ┌──────────────────────────────────────┐
  │ 检查权限                             │
  │ 请求的endpoint ∈ permissions[] ?     │
  └──────────────┬───────────────────────┘
                 ↓ 权限通过
  ┌──────────────────────────────────────┐
  │ 检查频率限制                         │
  │ 过去1小时请求数 < rate_limit ?       │
  └──────────────┬───────────────────────┘
                 ↓ 均通过
  ┌──────────────────────────────────────┐
  │ 允许访问 → 记录日志 → 返回数据       │
  └──────────────────────────────────────┘

Step 3: 外部系统生成签名
  signature = HMAC-SHA256(
    str(timestamp) + method + path + body_hash,
    client_secret
  )
```

本系统**不集成支付功能**，会员权限完全通过授权码激活实现。授权码是会员策略的执行载体。

```

│    }                                                         │

│    POST /api/v1/auth/activate                                │
│    Body: { "auth_code": "AIOS-MONTHLY-b2c3d4e5f6g7-abc2" }  │
│    系统验证：code_hash匹配 + status=active + 未过期            │

┌──────────────────────┴──────────────────────────────────────┐
```

```python
# 定时任务：每小时检查一次
def check_membership_expiry():
    expired_activations = db.query(AuthCodeActivation).filter(
        AuthCodeActivation.is_active == True,
        AuthCodeActivation.expires_at < datetime.now()
    ).all()
    
    for activation in expired_activations:
        activation.is_active = False
        # 检查用户是否还有其他有效激活
        other_active = db.query(AuthCodeActivation).filter(
            AuthCodeActivation.user_id == activation.user_id,
            AuthCodeActivation.is_active == True,
            AuthCodeActivation.id != activation.id
        ).first()
        
        if not other_active:
            # 无其他有效会员，降级为free
            user.role = 'free'
        else:
            # 有更高等级的会员仍然有效，保持最高等级
            user.role = max(other_active, key=lambda a: level_rank[a.activated_level]).activated_level
```

**授权码复用策略**：

| 类型 | 说明 | 用例 |
|------|------|------|
| 一次性授权码 | 激活后status→frozen，不可再用 | weekly/monthly/yearly个人开通 |
| 可复用授权码 | 激活后status保持active，多人可用 | enterprise企业批量对接 |
| 限量授权码 | max_activations限制激活次数 | 限量活动（如前50名用户） |

### 6.3 本地同步客户端设计 (api_client.py)

```python
# remote_sync/api_client.py 核心设计

class RemoteSyncClient:
    """
    替代原 NotionSyncClient，将所有Notion API调用改为FastAPI HTTP调用。
    
    原NotionSyncClient关键方法映射：
      notion_client_wrapper.py          →    api_client.py
      ─────────────────────────             ─────────────
      upsert_page(db_key, ...)         →    _sync_batch(endpoint, data_list)
      _get_existing_pages(db_key, ...) →    不再需要（服务端处理upsert）
      sync_opportunities(data)         →    sync_opportunities(data)
      sync_trends(data)                →    sync_trends(data)
      sync_risks(data)                 →    sync_risks(data)
      sync_platform_signals(data)       →    sync_platform_signals(data)
      sync_xhs_topics(data)            →    sync_xhs_topics(data)
      sync_user_emotions(data)         →    sync_user_emotions(data)
      verify_connection()              →    health_check()
    """
    
    def __init__(self, config_path="sync_config.json"):
        self.config = json.load(open(config_path))
        self.base_url = self.config["remote_host"]
        self.client_id = self.config["client_id"]
        self.client_secret = self.config["client_secret"]
        self.session = httpx.Client(timeout=30)
    
    def _sign_request(self, method, path, body=None):
        """生成请求签名（HMAC-SHA256）"""
        timestamp = str(int(time.time()))
        body_hash = hashlib.sha256(
            json.dumps(body or {}).encode()
        ).hexdigest()
        message = f"{timestamp}:{method}:{path}:{body_hash}"
        signature = hmac.new(
            self.client_secret.encode(),
            message.encode(),
            hashlib.sha256
        ).hexdigest()
        return {
            "X-Client-Id": self.client_id,
            "X-Timestamp": timestamp,
            "X-Signature": signature,
        }
    
    def _post_batch(self, endpoint, data_list):
        """批量推送数据到远程API"""
        headers = self._sign_request("POST", endpoint, data_list)
        headers["Content-Type"] = "application/json"
        
        resp = self.session.post(
            f"{self.base_url}{endpoint}",
            json={"items": data_list},
            headers=headers
        )
        resp.raise_for_status()
        return resp.json()
    
    def sync_opportunities(self, opportunities_data):
        """同步副业机会数据"""
        return self._post_batch(
            "/api/v1/sync/opportunities", 
            opportunities_data
        )
    
    def sync_trends(self, trends_data):
        return self._post_batch("/api/v1/sync/trends", trends_data)
    
    def sync_risks(self, risk_data):
        return self._post_batch("/api/v1/sync/risks", risk_data)
    
    def sync_platform_signals(self, signals_data):
        return self._post_batch("/api/v1/sync/platform-signals", signals_data)
    
    def sync_xhs_topics(self, topics_data):
        return self._post_batch("/api/v1/sync/xhs-topics", topics_data)
    
    def sync_user_emotions(self, emotions_data):
        return self._post_batch("/api/v1/sync/user-emotions", emotions_data)
    
    def health_check(self):
        """检查远程主机连接状态"""
        resp = self.session.get(f"{self.base_url}/api/v1/health")
        return resp.json()
```

## 八、情报系统展示方式决策

### 8.1 决策结论：静态优先 — 构建时生成 + Nginx 直出

**核心判断：情报站天然适合静态交付。**

本系统的数据生产链路是离线、单向、周期性的：

```
互联网采集 → 商业情报中转站（选题/去重/评分） → AI内容工厂（报告生成）
                                                      ↓
                                              远程情报中台（PG入库）
                                                      ↓
                                              【数据更新触发前端构建】
                                                      ↓
                                              Nginx 直接输出静态页面
```

数据一天最多更新一次，更新源是本地脚本推送，不是用户产生。这意味着：
- 不存在"用户发帖需要实时刷新"的场景
- 不存在"数据每秒变化需要 WebSocket"的场景
- 所有情报内容在两次同步之间是**完全不变的**

**因此，前端在同步完成后构建一次，Nginx 直接输出静态文件，是所有方案中最快的。**

### 8.2 静态方案如何解决"看似需要动态"的问题

| 顾虑 | 静态方案解法 |
|------|------------|
| "5级会员看到不同数据" | 同步脚本按会员等级预切 JSON 分片，前端登录后按 role 加载对应文件 |
| "搜索/筛选/排序" | 全量数据一次性加载到浏览器（情报站单表最多几百条），客户端 JS 筛选，速度远超 API 往返 |
| "Dashboard 实时计算" | 同步脚本预计算 TOP10、环比变化率，写入 `dashboard.json`，前端直接渲染 |
| "个性化收藏/标记已读" | localStorage 存储，纯客户端操作，不依赖服务端 |
| "授权码激活" | 唯一需要调 API 的场景，登录和激活走 FastAPI，其余全部静态 |

### 8.3 最终架构：Vue.js 静态构建 + 预计算 JSON + Nginx + FastAPI（仅鉴权）

```
用户浏览器
    │
    │  CF DNS → 域名解析到 Ubuntu 主机 IP
    ▼
Nginx (:80/443)
    │
    ├── /*.html, /*.js, /*.css  ──→  /var/www/intel-station/dist/   (静态文件，直接返回)
    ├── /data/*.json            ──→  /var/www/intel-station/data/    (预构建数据JSON)
    │
    └── /api/*                  ──→  FastAPI (:8000)                 (仅鉴权接口)
                                       ├── POST /auth/login
                                       ├── POST /auth/activate-code
                                       └── GET  /members/me
```

**请求比例估算**：
- 95% 请求命中 Nginx 静态文件（0ms 后端耗时）
- 5% 请求转发 FastAPI（仅登录和鉴权）

对比原动态 SPA 方案（每次页面切换都调 API），页面加载速度提升 **5-10 倍**。

### 8.6 前端加载流程（用户视角）

```

2. Nginx 返回 index.html（静态，<50ms）

6. 根据 role 动态加载对应 JSON：
   fetch('/data/monthly/dashboard.json')   ← Nginx 静态文件，<10ms
   fetch('/data/monthly/trends.json')      ← Nginx 静态文件，<10ms
7. 渲染 Dashboard 页面
```

**首屏完整时间**：首次访问约 500ms（JS 加载），二次访问约 100ms（全缓存）。

### 8.7 鉴权边界：API 只做两件事

```
所有 /api/* 请求 → FastAPI
    │
    ├── POST /api/auth/login          ← 用户名+密码 → 返回 JWT
    ├── POST /api/auth/activate-code   ← 授权码 → 升级会员等级
    ├── GET  /api/members/me           ← 验证 JWT → 返回当前角色
    │
    └── 其余一切数据读取 → 不走 API，走静态 JSON
```

**安全说明**：JSON 文件放在 Nginx 下，URL 可被猜测（如 `/data/yearly/trends.json`）。但这不影响安全，因为：

1. 情报数据本身不是高度机密（不是个人隐私数据）
2. 会员体系的价值在于**时效性+结构化分析**，不是数据本身不可见
3. 如果确实需要隐藏高级数据 URL，可以用 Nginx `secure_link` 模块做 URL 签名，或前端用 JWT role 做路由守卫（看不到高级页面就不会请求高级 JSON）

### 8.8 Nginx 配置要点

```nginx
server {
    listen 443 ssl http2;
    server_name intel.example.com;

    # SSL 证书（Let's Encrypt）
    ssl_certificate     /etc/letsencrypt/live/intel.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/intel.example.com/privkey.pem;

    root /var/www/intel-station/dist;

    # 静态文件（直接返回）
    location / {
        try_files $uri $uri/ /index.html;
        
        # 强缓存：带 hash 的 JS/CSS 文件永久缓存
        location ~* \.(js|css|woff2|png|jpg|svg)$ {
            expires 1y;
            add_header Cache-Control "public, immutable";
        }
        
        # 数据 JSON：短缓存（同步后即变）
        location /data/ {
            expires 300s;  # 5分钟，平衡新鲜度和性能
            add_header Cache-Control "public";
        }
    }

    # API 代理（仅鉴权）
    location /api/ {
        proxy_pass http://127.0.0.1:8000;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        
        # API 不限速（由 FastAPI 内部限流）
    }

    # Gzip 压缩
    gzip on;
    gzip_types text/html text/css application/javascript application/json;
    gzip_min_length 1000;
}
```

### 8.9 与动态方案的对比总结

| 维度 | 原动态 SPA 方案 | 静态优先方案 |
|------|----------------|-------------|
| 首屏加载 | 1.5-3s（API 往返） | 0.1-0.5s（Nginx 直出） |
| 页面切换 | 每次调 API | 切换路由即可（数据已在内存） |
| 服务器负载 | FastAPI 处理 95% 请求 | FastAPI 只处理 5% 鉴权请求 |
| 并发能力 | 受限于 FastAPI + PG | 受限于 Nginx（轻松上万并发） |
| 搜索筛选 | 每次调 API | 客户端毫秒级 |
| 数据新鲜度 | 实时 | 同步后 5 分钟内（expires 300s） |
| 部署复杂度 | 前端构建 + 后端部署 | 前端一次构建 + 替换 JSON |
| CF 配合 | 仅 DNS | DNS + 全站 CDN 缓存加速 |

**结论：静态优先方案在速度、并发、成本三个维度全面优于动态方案，且不损失任何功能。**

### 9.1 设计哲学：Notion 精神

本系统前端设计严格遵循 **Notion 式极简主义**，核心理念：

| 原则 | 说明 | 实施 |
|------|------|------|

| 留白呼吸 | 充足的负空间让页面"能呼吸" | 外间距≥32px，内间距≥16px，行高1.6+ |

| 排版即设计 | 字体层级和字重是唯一的视觉层次工具 | 3级标题 + 1种正文字号 + 1种辅助字号 |
| 无干扰交互 | 悬停才显示操作按钮，保持界面整洁 | hover时淡入（transition: opacity 150ms） |

### 9.9 视觉降噪策略

Notion风格的核心在于"视觉降噪"——把不重要的东西藏起来，让用户聚焦数据本身：

| 策略 | 实现方式 |
|------|---------|
| 操作按钮后置 | 列表行的编辑/删除按钮仅在hover时显示（opacity: 0 → 1） |
| 辅助信息淡化 | 时间戳、来源等元数据使用 --text-tertiary (#9B9B9B) 13px |
| 图标最小化 | 仅导航使用16px线性图标（Lucide Icons风格），页面内不用装饰图标 |
| 无分割线堆叠 | 同组内容用间距区分，不用分割线（Notion卡片列表特征） |
| 数据密度控制 | 默认显示关键字段，详情按需展开（"显示更多 ↓"） |
| 色彩克制 | 一个页面不超过3种语义色同时出现 |
| 滚动渐进显示 | 长列表底部渐隐遮罩，暗示可滚动 |

### 10.1 核心数据表（从Notion 6库一对一映射）

```sql
-- ============================================
-- 1. trends（趋势数据库）
-- 来源：原Notion 🔥 趋势数据库（16个属性）
-- 本地源：trend_db.json
-- ============================================
CREATE TABLE trends (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    name            VARCHAR(256) NOT NULL,                      -- 趋势名称（TITLE，唯一键）
    platform        VARCHAR(64),                                -- 平台：小红书/抖音/视频号/B站
    category        JSONB DEFAULT '[]',                         -- 分类（multi-select → JSONB数组）
    direction       VARCHAR(32),                                -- 趋势方向：快速上升/上升/平稳/下降
    opportunity_score DECIMAL(5,1),                             -- 机会评分 0-100
    lifecycle       VARCHAR(32),                                -- 生命周期：早期/爆发期/饱和期/衰退期
    peak_expected   DATE,                                       -- 预期达峰
    first_observed  DATE,                                       -- 首次发现
    competition     VARCHAR(32),                                -- 竞争度：低/中等/高/极高
    risk_level      VARCHAR(32),                                -- 风险等级：low/medium/high/critical
    monetization    VARCHAR(32),                                -- 变现能力：高/中等/低
    actionable_insight TEXT,                                    -- 行动建议
    risk_note       TEXT,                                       -- 风险备注
    evidence        TEXT,                                       -- 证据描述
    status          VARCHAR(32) NOT NULL DEFAULT 'active',      -- active/monitoring/peaked/declining
    metadata        JSONB DEFAULT '{}',                         -- 扩展字段
    
    -- 同步追踪
    source_file     VARCHAR(256),                              -- 来源JSON文件
    source_id       VARCHAR(64),                               -- 来源数据中的ID
    sync_version    INTEGER NOT NULL DEFAULT 1,                -- 同步版本号
    
    created_at      TIMESTAMP NOT NULL DEFAULT NOW(),
    updated_at      TIMESTAMP NOT NULL DEFAULT NOW(),
    
    -- upsert使用name作为业务唯一键
    CONSTRAINT uq_trends_name UNIQUE (name)
);

CREATE INDEX idx_trends_platform ON trends(platform);
CREATE INDEX idx_trends_direction ON trends(direction);
CREATE INDEX idx_trends_lifecycle ON trends(lifecycle);
CREATE INDEX idx_trends_score ON trends(opportunity_score DESC);
CREATE INDEX idx_trends_status ON trends(status);
CREATE INDEX idx_trends_created ON trends(created_at DESC);


-- ============================================
-- 2. opportunities（副业机会数据库）
-- 来源：原Notion 💰 副业机会数据库（32个属性）
-- 本地源：opportunity_db.json
-- ============================================
CREATE TABLE opportunities (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    name            VARCHAR(256) NOT NULL,                      -- 机会名称（唯一键）
    category        VARCHAR(64),                               -- 分类
    sub_category    VARCHAR(64),                               -- 子分类
    verdict         VARCHAR(32),                               -- 判断结果：RECOMMENDED/CAUTION/AVOID
    verdict_score   DECIMAL(5,1),                              -- 机会评分 0-100
    difficulty      VARCHAR(32),                               -- 难度：easy/medium/hard
    startup_cost    DECIMAL(12,2),                             -- 启动成本
    monthly_ceiling TEXT,                                      -- 月收入天花板
    time_to_first_revenue TEXT,                                -- 首次收入时间
    risk_level      VARCHAR(32),                               -- 风险等级
    lifecycle_stage VARCHAR(32),                               -- 生命周期
    trend_direction VARCHAR(32),                               -- 趋势方向
    persona_fit     JSONB DEFAULT '[]',                        -- 适用人群（数组）
    platforms       JSONB DEFAULT '[]',                        -- 平台（数组）
    
    -- key_metrics
    search_growth           TEXT,                               -- 搜索增长
    competitor_count        TEXT,                               -- 竞争数量
    content_saturation      VARCHAR(32),                        -- 内容饱和度
    monetization_readiness  VARCHAR(32),                        -- 变现就绪度
    
    -- 时间追踪
    first_identified DATE,                                      -- 首次识别
    last_verified    DATE,                                      -- 最近验证
    
    -- 商业路径 (1-4)
    commercial_path_1 TEXT,                                     -- 商业路径1描述
    price_range_1    TEXT,                                     -- 价格区间1
    commercial_path_2 TEXT,
    price_range_2    TEXT,
    commercial_path_3 TEXT,
```

### 10.2 upsert存储过程

```sql
-- 趋势表 upsert函数（替代原Notion upsert_page逻辑）
CREATE OR REPLACE FUNCTION upsert_trend(
    p_name VARCHAR(256),
    p_data JSONB
) RETURNS TABLE(action VARCHAR(16), item_id UUID) AS $$
DECLARE
    v_existing_id UUID;
BEGIN
    SELECT id INTO v_existing_id FROM trends WHERE name = p_name;
    
    IF v_existing_id IS NOT NULL THEN
        -- 更新
        UPDATE trends SET
            platform = COALESCE(p_data->>'platform', platform),
            direction = COALESCE(p_data->>'direction', direction),
            opportunity_score = COALESCE((p_data->>'opportunity_score')::DECIMAL, opportunity_score),
            lifecycle = COALESCE(p_data->>'lifecycle', lifecycle),
            status = COALESCE(p_data->>'status', status),
            updated_at = NOW(),
            sync_version = sync_version + 1
        WHERE id = v_existing_id;
        
        action := 'updated';
        item_id := v_existing_id;
    ELSE
        -- 插入
        INSERT INTO trends (name, platform, category, direction, opportunity_score, 
                           lifecycle, status, evidence, actionable_insight, risk_note)
        VALUES (
            p_name,
            p_data->>'platform',
            COALESCE((p_data->'category')::JSONB, '[]'),
            p_data->>'direction',
            (p_data->>'opportunity_score')::DECIMAL,
            p_data->>'lifecycle',
            COALESCE(p_data->>'status', 'active'),
            p_data->>'evidence',
            p_data->>'actionable_insight',
            p_data->>'risk_note'
        )
        RETURNING id INTO item_id;
        
        action := 'created';
    END IF;
    
    RETURN NEXT;
END;
$$ LANGUAGE plpgsql;
```

## 十三、安全设计

### 13.1 三层鉴权体系

```
第一层：会员用户 → JWT Token + 授权码激活
  - 用户注册后默认为free等级
  - 通过授权码激活升级为weekly/monthly/yearly
  - Token中包含role字段（free/weekly/monthly/yearly/enterprise）
  - API按role过滤返回数据（如weekly只能看TOP5趋势）
  - 会员到期自动降级为free

第二层：企业对接 → API Key (HMAC签名)
  - enterprise等级的授权码自动生成client_id + client_secret
  - 每次请求计算HMAC-SHA256签名
  - 服务端验证签名+检查permissions+频率限制

第三层：本地同步 → 独立授权码
  - 本地系统持有唯一的sync授权码
  - 仅能访问 /api/v1/sync/* 端点
  - 最高频率限制（避免误操作大量写入）
```

### 13.2 API安全措施

| 措施 | 实现 | 说明 |
|------|------|------|
| HTTPS | Nginx + Let's Encrypt | 全站加密传输 |
| JWT过期 | access_token 1h, refresh_token 7d | 短期+刷新机制 |
| API签名 | HMAC-SHA256 | 防篡改+防重放(timestamp校验) |
| 频率限制 | Redis + FastAPI middleware | 每client_id每小时N次 |
| IP白名单 | Nginx allow/deny | sync接口仅允许本地IP |
| 输入验证 | Pydantic Schema | 所有请求体验证 |
| SQL注入防护 | SQLAlchemy ORM | 参数化查询 |
| CORS | FastAPI CORSMiddleware | 仅允许前端域名 |
| 日志审计 | sync_log + auth_code_usage_logs | 全量操作记录 |

### 13.3 授权码安全策略

```
1. 授权码仅在创建时返回明文一次，之后不可查看
2. 数据库中仅存储SHA256哈希值
3. 服务端通过比对哈希值验证授权码有效性
4. 支持冻结/吊销/过期状态管理
5. 使用日志记录所有API调用（含IP、端点、状态码）
6. 异常调用自动告警（频率突增、异常IP）
```
