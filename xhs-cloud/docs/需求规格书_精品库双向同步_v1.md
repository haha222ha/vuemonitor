## 0. 文档用途（请先读）

本文档面向 **APP 采集机（Windows）+ 云主机（Linux）+ 家里 Agent（Windows）** 三端协同实施。

**目标读者**：在 APP 采集机上部署的工程师（不一定是写文档这台电脑）。

**读完本文档你应能**：

1. 理解为什么要从「云扫 15 万 API」改为「本地精品库主扫 + 云只补缺口 + 云出报告」
2. 知道三端各自职责、数据库表结构、同步 API 约定
3. 按 **Phase 1~4**  checklist 逐步实施并验收

**实施原则**：

- **本地 APP = 主采集**（关键词 + trade_note，稳定、成本低）
- **精品库 `premium_goods.db` = 同步中枢**（必须带 `primary_keyword`）
- **云主机 = 报告生成 + 缺口小批量补齐**（不再 15 万/datacenter IP 硬扫）
- **家里 Agent = risk/fail 住宅 IP 补扫**（batch=80, api_only）

## 1. 背景与现状问题

### 1.1 当前数据流（as-is）

```
本地 SQLite 全库 (~1280万 goods)
    ↓ gen_report 选品（实体 v1d>5 / 虚拟 v1d>1）
D:\选品报告\全量MMDD\data.js
    ↓ cloud_sync / scp
云 PG monitor_goods (~15万, v1d>0 入池)
    ↓ cloud_daemon goods_id API 直扫 (1000/批)
云 + 家里 Agent 补 risk
    ↓
cloud_gen_report 生成会员报告
```

### 1.2 已暴露的问题（2026-06-23/24 实测）

| 现象 | 根因 |
|------|------|
| 云 ok 仅 ~15%，risk ~12 万 | 香港 datacenter IP 对 goods_id API 大面积限流/不确定 |
| riskFR 批次 ok=1~4/1000 | 云对 risk 反复 API 补扫几乎无效 |
| 家里 Agent ok=80/80 | 住宅 IP 仍有效 |
| 15 万品无法 keyword 覆盖 | 同步 PG **无 primary_keyword**，与 APP 词包体系脱节 |
| 需 1 万+ 词覆盖 vs 4000 词/天 | 用 goods_id 直扫思路错误；APP 应 **一词多品** |

### 1.3 业务约束（已确认）

| 约束 | 说明 |
|------|------|
| APP 搜索 | **必须带完整 primary_keyword**，不能 goods_id 直查列表 |
| trade_note | ~**15 万/设备/天**，按 keyword 聚合刷新 |
| mall_list | ~**2 万/账号/天**，含 behavior_tags |
| 关键词搜索极限 | 全账号合计 ~**4000 词/天** |
| 云 Web/API | datacenter IP **不能**承担 15 万/天主扫 |
| 精品库 | 持续增长，需 lifecycle 升降级 |

## 2. 目标架构（to-be）

### 2.1 三层业务

| 层 | 名称 | 库/产物 | 职责 |
|----|------|---------|------|
| **L1** | 发现层 | `xhs_burst_monitor.db` | 4000 词/天探索新品（`D:\关键词搜索` 词库轮转） |
| **L2** | 选品层 | `D:\选品报告\全量MMDD\` | 日报/周报，决定谁 **有资格** 进精品库 |
| **L3** | 精品层 | `premium_goods.db` ↔ 云 `premium_goods` | **主监控对象**，APP 词包扫描，双向同步 |

### 2.3 三端职责一览

| 端 | 做什么 | 不做什么 |
|----|--------|----------|
| **APP 采集机** | L1 发现、L3 精品 APP 扫描、ingest、推云、拉云变更 | 不指望云扫 15 万 |
| **云主机** | PG 镜像、缺口小批 API 补扫、生成报告、会员分发 | 不全池/datacenter 硬扫、不主扫 risk |
| **家里 Agent** | risk/fail 住宅 IP 补扫 | 不做 L1 发现、不扫全池 |

## 3. 关键词库（D:\关键词搜索）

### 3.1 文件清单

| 文件 | 词数（行数） | 用途 |
|------|-------------|------|
| `最终版_实体产品搜索词库.txt` | **15,716** | L1 实体类探索 |
| `最终版_虚拟产品搜索词库.txt` | **23,493** | L1 虚拟类探索 |
| **合计** | **~39,209** | 10 天 @4000词/天 可轮转一轮 |

> **路径**：采集机上复制到固定目录，例如 `D:\关键词搜索\` 或 `{爬虫根目录}\keyword_packs\`。

### 3.2 词库结构说明

词库含大量 **「核心词 + 后缀变体」**，例如：

```
DIY日历
DIY日历ins风
DIY日历学生党
...
```

**禁止**把 39k 行全部当作独立探索词一次性灌入 L1（浪费配额、重复严重）。

### 3.3 推荐使用方式

| 用途 | 策略 |
|------|------|
| **L1 发现** | 4000 词/天：~2000 核心词 + ~2000 变体，**10 天轮转** 39k |
| **L3 精品 primary_keyword** | **不用词库盲绑**；优先 `goods.keyword` → `goods_keywords` 命中最高 → 词库标题模糊匹配 |
| **L3 fallback_keywords** | 主词失效时，从同品类词库变体取 3~5 个 |

### 3.4 词库导入脚本（待建）

**文件**：`tools/import_keyword_pack.py`（建议放在爬虫根目录或 xhs-cloud/tools）

**逻辑**：

1. 读两个 txt，每行一词
2. 提取核心词（可选：去常见后缀 ins风/学生党/高级感…）
3. 写入主库 `keyword_pool`：`tier=S/A/B`, `category=physical|virtual`, `source=pack_v1`
4. 写 `keyword_batches` 四批（每周一批，与 v2 文档 §8 一致）

**验收**：`SELECT COUNT(*) FROM keyword_pool WHERE source='pack_v1'` ≈ 39209；每日 L1 调度取 4000 词不重复超 10 天。

### 4.2 云 PG 镜像表（待建）

**迁移文件**：`xhs-cloud/cloud_deploy/database/migrations/002_premium_goods.sql`

```sql
SET search_path TO xhs_monitor, public;

CREATE TABLE IF NOT EXISTS premium_goods (
    goods_id              VARCHAR(32) PRIMARY KEY,
    title                 TEXT,
    is_virtual            BOOLEAN DEFAULT FALSE,
    tier                  VARCHAR(8) DEFAULT 'B',
    lifecycle             SMALLINT DEFAULT 0,
    primary_keyword       TEXT NOT NULL,
    fallback_keywords     JSONB DEFAULT '[]',
    store_id              VARCHAR(64),
    store_name            VARCHAR(256),
    deal_price            NUMERIC(12,2) DEFAULT 0,
    sold_num              INTEGER DEFAULT 0,
    velocity_1d           NUMERIC(12,2) DEFAULT 0,
    actual_velocity_1d    NUMERIC(12,2) DEFAULT 0,
    burst_score           NUMERIC(12,2) DEFAULT 0,
    scan_priority         INTEGER DEFAULT 50,
    monitor_freq          VARCHAR(16) DEFAULT 'daily',
    -- 扫描来源与时间
    last_app_scan         TIMESTAMPTZ,
    last_cloud_scan       TIMESTAMPTZ,
    last_agent_scan       TIMESTAMPTZ,
    last_scan_status      VARCHAR(16),
    last_scan_engine      VARCHAR(32),
    scan_owner            VARCHAR(16) DEFAULT 'local',  -- local | cloud | agent
    -- 同步
    sync_version          BIGINT DEFAULT 0,
    source                VARCHAR(32) DEFAULT 'premium_ingest',
    created_at            TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at            TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE INDEX IF NOT EXISTS idx_pg_kw ON premium_goods (primary_keyword) WHERE lifecycle < 3;
CREATE INDEX IF NOT EXISTS idx_pg_gap ON premium_goods (lifecycle, last_app_scan, scan_priority DESC);
CREATE INDEX IF NOT EXISTS idx_pg_sync ON premium_goods (updated_at, sync_version);

-- 同步水位（每端一条）
CREATE TABLE IF NOT EXISTS premium_sync_cursor (
    client_id   VARCHAR(64) PRIMARY KEY,  -- local_app | cloud | agent:ID
    last_version BIGINT DEFAULT 0,
    last_pull_at TIMESTAMPTZ,
    last_push_at TIMESTAMPTZ
);
```

**与现有 `monitor_goods` 关系**：

- `monitor_goods`：**保留**，服务报告统计、历史兼容
- **新扫描队列以 `premium_goods` 为准**
- 报告生成 (`pg_reader.py`) Phase 2 后可改为读 `premium_goods` + `goods_sold_daily`

### 4.3 精品入池规则

| 来源 | 条件 | tier 初值 |
|------|------|-----------|
| 日报 TOP | pool IN (BURST, ACCEL) 或 actual_v1d 前 10% | S/A |
| 日报普通入选 | 通过 v1d/actual 阈值 | B |
| L1 新爆品 | 实体 v1d>5 / 虚拟 v1d>1 + 有 keyword | B |

**出池/降频**：

## 5. 双向同步协议

### 5.1 认证

与现有推云一致：

- Header: `X-Sync-Key: {与云 .env XHS_CLOUD_SYNC_KEY 一致}`
- Base URL: `https://monitor.xhs365.cn` 或 `XHS_CLOUD_API_URL`

### 5.2 API 列表（待实现）

#### POST `/api/v1/sync/premium-upsert`

**方向**：本地 → 云  
**触发**：精品批扫完 / 每 5 分钟定时 / ingest 后

**请求体**：

```json
{
  "client_id": "local_app:COMPUTERNAME",
  "sync_version": 12345,
  "rows": [
    {
      "goods_id": "xxx",
      "title": "...",
      "primary_keyword": "完整搜索词",
      "tier": "A",
      "lifecycle": 0,
      "sold_num": 1200,
      "velocity_1d": 15.2,
      "actual_velocity_1d": 12.0,
      "burst_score": 85,
      "last_app_scan": "2026-06-24T08:00:00+08:00",
      "last_scan_status": "ok",
      "scan_owner": "local",
      "updated_at": "2026-06-24T08:00:01+08:00"
    }
  ]
}
```

**响应**：

```json
{
  "accepted": 80,
  "rejected": 0,
  "server_version": 12346,
  "conflicts": []
}
```

#### GET `/api/v1/sync/premium-changes?since={version}&limit=500`

**方向**：云 → 本地  
**触发**：本地 daemon 每 5~15 分钟拉一次

**响应**：同上 `rows` 数组 + `latest_version`

**用途**：拉回云缺口补扫、家里 Agent 补扫结果。

#### POST `/api/v1/sync/premium-catalog`

**方向**：双向目录对账（每日 1 次）

**请求**：`{"local_ids": ["..."], "since_date": "2026-06-24"}`  
**响应**：`{"cloud_only": [...], "local_only": [...]}` → 各自 ingest

### 5.3 冲突解决规则

| 字段 | 规则 |
|------|------|
| sold_num, velocity_* | **取 updated_at 更新者**；同秒则按优先级：`local_app` > `local_web` > `agent` > `cloud` |
| primary_keyword | **始终以本地为准**（云不改词） |
| lifecycle | 取 **更严格** 状态（归档 > 降频 > 观察 > 活跃）需人工复核时可打 flag |
| sync_version | 服务端递增；客户端只接受 `server_version > local_version` |

## 6. 云主机：缺口补齐 + 报告

### 6.1 cloud_daemon 改造目标

**当前（需废弃）**：

```
daily 首轮全池 15万 → 休12h → risk全池 1000/60s 循环
```

**目标**：

```
仅扫 gap_queue（本地 24h 未 APP 更新 且 lifecycle<3）
批量 500，冷却 120s
无 gap → 休眠 1h 再检查
不跑 risk 全池（交给家里 Agent）
```

### 6.2 gap 判定 SQL

```sql
SELECT goods_id, title, primary_keyword, tier, scan_priority
FROM premium_goods
WHERE lifecycle IN (0, 1)
  AND (
    last_app_scan IS NULL
    OR last_app_scan < NOW() - INTERVAL '24 hours'
  )
  AND (last_cloud_scan IS NULL OR last_cloud_scan < NOW() - INTERVAL '6 hours')
ORDER BY
  CASE tier WHEN 'S' THEN 1 WHEN 'A' THEN 2 WHEN 'B' THEN 3 ELSE 4 END,
  scan_priority DESC,
  last_app_scan ASC NULLS FIRST
LIMIT 500;
```

### 6.3 daemon.json 建议配置

```json
{
  "batch_size": 500,
  "web_cooldown_seconds": 120,
  "web_detail_concurrency": 2,
  "skip_today": true,
  "pool_cycle": {
    "enabled": true,
    "pause_hours": 12,
    "claim_ttl_minutes": 25,
    "mode": "gap_only"
  },
  "risk_rescan": { "enabled": false }
}
```

> `mode: gap_only` 需在 `cloud_daemon.py` Phase 1 代码中实现（读 `premium_goods` 而非全池）。

### 6.4 systemd 环境

`/etc/systemd/system/xhs-daemon.service` 关键项：

```ini
Environment=XHS_DAEMON_BATCH_SIZE=500
Environment=XHS_DAEMON_COOLDOWN_SEC=120
Environment=XHS_DAEMON_CONCURRENCY=2
Environment=XHS_ENABLE_PLAYWRIGHT=0
```

**注意**：systemd 的 `Environment=` 会覆盖 `daemon.json`，改 json 后必须同步改 service。

### 6.5 报告生成（保持）

```bash
# 已有 timer
systemctl list-timers | grep xhs-daily-report
# 17:00 cloud_gen_report → PG → zip → 会员下载
```

报告数据源 Phase 1 仍用 `monitor_goods + goods_sold_daily`；Phase 3 切 `premium_goods`。

## 12. 风险与对策

| 风险 | 对策 |
|------|------|
| primary_keyword 缺失导致 APP 无法扫 | ingest 后强制 `--resolve-keywords`；无词则 lifecycle=3 不入队 |
| 双写冲突 | sync_version + scan_owner 优先级 |
| 云仍被限流 | 云只扫 gap 小批；主扫必须在 APP |
| 采集机离线 | 云 gap 队列积压；恢复后 catalog 对账 |
| 词库版权/重复 | 核心词去重；L1 批内去重 |
| 迁移期双 daemon | feature flag `pool_cycle.mode=gap_only` 灰度 |
