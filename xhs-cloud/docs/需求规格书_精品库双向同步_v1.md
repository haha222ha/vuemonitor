## 0. 文档用途（请先读）

> **便携说明**：整块 **D: 移动硬盘** 即完整工作区。插入任意 Windows 电脑后，用 Cursor / VS Code **打开文件夹 `D:\vuemonitor`**（或 `D:\`），AI 与工程师均按本文 **§0.1 路径常量** 读写，**不要**依赖 `C:\Users\...\AppData` 下的路径。

本文档面向 **D 盘 APP 采集机 + 云主机（Linux）+ 家里 Agent（可选同盘 D:\）** 三端协同实施。

**目标读者**：在 **插入 D 盘的那台电脑** 上实施的人员或 AI Agent。

**读完本文档你应能**：

1. 理解为什么要从「云扫 15 万 API」改为「本地精品库主扫 + 云只补缺口 + 云出报告」
2. 知道三端各自职责、数据库表结构、同步 API 约定
3. 按 **§0.1 路径** 与 **§9 Phase 1~4**  checklist 逐步实施并验收

**实施原则**：

- **D 盘 = 便携工作区**（vuemonitor、词库、报告、配置在 D:；**爬虫根目录由你在配置里指定**）
- **本地 APP = 主采集**（关键词 + trade_note，稳定、成本低）
- **精品库 `premium_goods.db` = 同步中枢**（必须带 `primary_keyword`）
- **云主机 = 报告生成 + 缺口小批量补齐**（不再 15 万/datacenter IP 硬扫）
- **家里 Agent = risk/fail 住宅 IP 补扫**（batch=80, api_only）

#### 0.5.3 Pull — 新电脑拉最新代码（**不需要 GitHub 登录**）

插入 D 盘后，在 PowerShell 执行（一键脚本）：

```powershell
powershell -ExecutionPolicy Bypass -File D:\vuemonitor\xhs-cloud\templates\portable\git_pull.ps1
```

或手动：

```powershell
$git = "D:\PortableGit\cmd\git.exe"
& $git -C D:\vuemonitor fetch origin main
& $git -C D:\vuemonitor pull origin main
& $git -C D:\vuemonitor log -1 --oneline
```

**期望**：最后一行显示较新的 commit（如 `feat(xhs-cloud): ...`），无 `Authentication failed`。

> 若 `pull` 报本地有未提交改动冲突：先 `git status` 看清文件；开发代码应在 `xhs-cloud/`，**不要**改 `.env`、数据库、报告等大文件。必要时 `git stash` 再 pull。

#### 0.5.4 Push — 本机改完代码推上 GitHub（**需要一次性登录**）

**日常推荐**：用仓库自带脚本（自动找 PortableGit、只提交 `xhs-cloud/`）：

```powershell
cd D:\vuemonitor
powershell -ExecutionPolicy Bypass -File scripts\push-xhs-cloud.ps1
```

针对 Agent / risk 补扫等专项改动，也可用：

```powershell
powershell -ExecutionPolicy Bypass -File D:\vuemonitor\xhs-cloud\tools\git_push_risk_rescan.ps1
powershell -ExecutionPolicy Bypass -File D:\vuemonitor\xhs-cloud\tools\git_push_agent.ps1
```

**手动 push**（与上面脚本等价）：

```powershell
$git = "D:\PortableGit\cmd\git.exe"
Set-Location D:\vuemonitor
& $git status -sb
& $git add xhs-cloud/
& $git commit -m "feat(xhs-cloud): 你的改动说明"
& $git push origin main
```

##### 首次 push 时 GitHub 登录（三选一，任选一种成功即可）

**方式 1 — 凭据管理器弹窗（我们之前成功的做法）**

```powershell
cd D:\vuemonitor
scripts\reopen-git-login.bat
```

脚本会尝试 `git credential-manager github login`；若弹出浏览器，按提示在 https://github.com/login/device 输入设备码完成授权。成功后 Windows 会**记住凭据**，以后 push 不再登录。

**方式 2 — push 时浏览器授权**

```powershell
D:\PortableGit\cmd\git.exe -C D:\vuemonitor push origin main
```

弹出 GitHub 登录 / 设备码页面 → 登录 `haha222ha` 账号 → 授权。

**方式 3 — Personal Access Token（无浏览器弹窗时）**

1. 浏览器打开 GitHub → Settings → Developer settings → Personal access tokens → Generate（勾选 `repo`）
2. 复制 token（只显示一次）
3. push 时：**用户名**填 GitHub 用户名，**密码**粘贴 token（不是 GitHub 登录密码）

> **禁止**把 token、`.env` 里的 `XHS_CLOUD_SYNC_KEY` 提交进 git。`.env` 已在 `.gitignore`。

#### 0.5.5 云主机 Pull + 部署（SSH，已验证流程）

本地 push 成功后，SSH 登录云主机执行：

```bash
cd /opt/vuemonitor
git fetch origin main
git pull origin main
git log -1 --oneline

rsync -a /opt/vuemonitor/xhs-cloud/ /opt/xhs-cloud/ \
  --delete --exclude data --exclude venv --exclude .env

# 若改了 systemd 单元（如 cooldown），需额外复制：
sudo cp /opt/xhs-cloud/cloud_deploy/systemd/xhs-daemon.service /etc/systemd/system/xhs-daemon.service
sudo systemctl daemon-reload

cd /opt/xhs-cloud && bash cloud_deploy/scripts/host-update.sh
sudo systemctl restart xhs-daemon xhs-cloud-api
```

**云主机首次 clone**（仅 `/opt/vuemonitor` 尚不存在时）：

```bash
sudo mkdir -p /opt
cd /opt
sudo git clone https://github.com/haha222ha/vuemonitor.git vuemonitor
sudo chown -R $USER:$USER /opt/vuemonitor
```

> 云主机对**公开仓库** clone/pull **不需要** GitHub 登录；若仓库改为私有，需在服务器配置 Deploy Key 或 PAT（与本节 Windows 登录无关）。

#### 0.5.6 端到端同步顺序（代码 vs 业务数据）

```
Windows 改 xhs-cloud 代码
    → git push（§0.5.4）
    → 云 SSH git pull + rsync + host-update（§0.5.5）

Windows 精品库 / 报告等业务数据
    → HTTP API cloud_sync_premium / cloud_sync_client（§5，用 XHS_CLOUD_SYNC_KEY）
```

#### 0.5.7 常见问题

| 现象 | 处理 |

## 1. 背景与现状问题

### 1.1 当前数据流（as-is）

```
本地 SQLite 全库 (~1280万 goods)
    ↓ gen_report 选品（实体 v1d>5 / 虚拟 v1d>1）
D:\选品报告\全量MMDD\data.js
    ↓ cloud_sync / scp
云 PG monitor_goods (~15万, v1d>0 入池)
    ↓ cloud_daemon goods_id API 直扫 (1000/批)
云 + 家里 Agent 补 risk
    ↓
cloud_gen_report 生成会员报告
```

### 1.2 已暴露的问题（2026-06-23/24 实测）

| 现象 | 根因 |
|------|------|
| 云 ok 仅 ~15%，risk ~12 万 | 香港 datacenter IP 对 goods_id API 大面积限流/不确定 |
| riskFR 批次 ok=1~4/1000 | 云对 risk 反复 API 补扫几乎无效 |
| 家里 Agent ok=80/80 | 住宅 IP 仍有效 |
| 15 万品无法 keyword 覆盖 | 同步 PG **无 primary_keyword**，与 APP 词包体系脱节 |
| 需 1 万+ 词覆盖 vs 4000 词/天 | 用 goods_id 直扫思路错误；APP 应 **一词多品** |

### 1.3 业务约束（已确认）

| 约束 | 说明 |
|------|------|
| APP 搜索 | **必须带完整 primary_keyword**，不能 goods_id 直查列表 |
| trade_note | ~**15 万/设备/天**，按 keyword 聚合刷新 |
| mall_list | ~**2 万/账号/天**，含 behavior_tags |
| 关键词搜索极限 | 全账号合计 ~**4000 词/天** |
| 云 Web/API | datacenter IP **不能**承担 15 万/天主扫 |
| 精品库 | 持续增长，需 lifecycle 升降级 |

## 2. 目标架构（to-be）

### 2.1 三层业务

| 层 | 名称 | 库/产物 | 职责 |
|----|------|---------|------|
| **L1** | 发现层 | `xhs_burst_monitor.db` | 4000 词/天探索新品（`D:\关键词搜索` 词库轮转） |
| **L2** | 选品层 | `D:\选品报告\全量MMDD\` | 日报/周报，决定谁 **有资格** 进精品库 |
| **L3** | 精品层 | `premium_goods.db` ↔ 云 `premium_goods` | **主监控对象**，APP 词包扫描，双向同步 |

### 4.5 店铺粉丝增量与「重点观察店铺」（全自动报告维度）

#### 4.5.1 设计意图（产品定位）

| 是 | 否 |
|----|-----|
| **店铺级**信号：哪些店值得重点观察 | 要求同店每个 SKU 粉丝增量完全一致 |
| 全自动日报/周报输出 **「参考维度」**（标签、排序、专题池） | 会员逐商品核对粉丝数 |
| 系统标店 → 报告列出店 + **代表商品** → 人再下钻追查同店其他 SKU | 人工先找店再开报表 |

**结论**：`shop_fans_delta`、连续涨粉 streak 的 **权威计算在 `premium_store_daily`（店维度）**；`premium_goods` 上的 `shop_fans` / `shop_fans_delta_1d` 仅为 **JOIN 冗余**，便于商品列表带店标签，**不作为店级分析真源**。同店多品数值瞬时不一致 **可接受**，以 **`store_id` 在 `premium_store_daily` 的最新店快照** 为准。

#### 4.5.2 数据模型（店真源 + 商品冗余）

| 层 | 表/字段 | 说明 |
|----|---------|------|
| **店日快照（真源）** | `premium_store_daily` | `store_id + snap_date`：`shop_fans`、`shop_sales`、`shop_fans_delta` |
| **店观察衍生（报告用）** | `premium_store_watch` | 每日批算：`streak_fans_up_days`、`sum_actual_delta_7d`、`watch_score`、`watch_tags`（§4.7.1） |
| 商品当前行（冗余） | `premium_goods.shop_fans`、`shop_fans_delta_1d` | 从店快照 **广播** 到同店商品，供商品表筛选/排序 |
| 商品日快照 | `premium_goods_daily` | **只存销量/价格**；**不存**粉丝历史（粉丝历史只在店表） |

**日增量计算**（仅 `premium_store_daily`）：

```python

prev = SELECT shop_fans FROM premium_store_daily
       WHERE store_id=? AND snap_date < today ORDER BY snap_date DESC LIMIT 1
delta = shop_fans - prev.shop_fans if prev and shop_fans > 0 else 0
UPSERT premium_store_daily (store_id, snap_date, shop_fans, shop_fans_delta, ...)
UPDATE premium_goods SET shop_fans=?, shop_fans_delta_1d=? WHERE store_id=?  -- 冗余广播
CALL recompute_store_watch(store_id)
```

- 店日快照历史：`premium_store_daily` 随 `premium-snapshots-backfill` 上传（§4.6）
- 店观察表：每日报告前云侧 `recompute_all_store_watch()`；`premium_store_watch` 供报告只读
- 商品行冗余：`shop_fans`、`shop_fans_delta_1d`、`store_watch_tags` 随 `premium-upsert` 推送

报告 **自动** 产出店维度参考（会员默认看「重点观察店铺」，再点店下钻 SKU）：

### 4.6 入选精品：历史快照全量上传（报告准确性）

> **目标**：商品 **一入精品库**，就把本地主库中该 `goods_id` 的 **全部历史日快照** 推到云 PG，使云生成的日报/周报能算 **连续上涨、连续观察、新店涨粉** 等维度，而不是只有「入池日」之后的数据。

#### 4.6.1 快照来源（本地）

| 优先级 | 数据源 | 路径 |
|--------|--------|------|
| 1 | 主库 `sold_history` / 日快照表 | `{XHS_CRAWLER_ROOT}\crawl_data\xhs_burst_monitor.db` |
| 2 | 精品库自建 `premium_goods_daily` | 入池后每日扫描追加 |
| 3 | 店铺粉丝 | `store_scores` 或历史 `premium_store_daily` |

**ingest 时触发**（`xhs_premium_ingest.py` 扩展）：

```
1. INSERT/UPDATE premium_goods 当前行
2. 若 premium_sync_state.snapshots_backfill_done = 0：
     a. 从主库导出该 goods_id 全部 sold 日快照 → premium_goods_daily（source=backfill）
     b. 若有 store_id，导出粉丝相关历史 → premium_store_daily
     c. POST premium-snapshots-backfill（分批，每批 ≤500 行）
     d. 标记 snapshots_backfill_done = 1
3. 日常扫描：仅追加「今日」一行 premium_goods_daily + push 增量
```

```json
      "shop_fans": 1200,
      "shop_sales": 50000,
      "shop_fans_delta": 15,
      "source": "backfill"
    }
  ]
}
```

**云侧写入规则**：

- `premium_goods_daily`：`ON CONFLICT (goods_id, snap_date) DO UPDATE`，**仅当 incoming.source=backfill 且本地无行，或 incoming.actual_delta 更新** 时覆盖
- `premium_store_daily`：同上，按 `store_id + snap_date`
- 更新 `premium_sync_state.snapshots_backfill_rows`
- **不回填** `monitor_goods` / 全池 `goods_sold_daily`（避免污染 15 万池）

**体量控制**：

- 单商品历史通常 ≤90~365 行；精品池 5k~30k 品分批上传（夜间 `backfill --all-pending`）
- 首批入池可限制 `backfill --max-days 90`，周报需要时再 `--extend 180`

#### 4.7.1 店铺维度（重点观察店 — 报告一级入口）

数据源：`premium_store_daily` + `premium_store_watch` + 池内 `premium_goods` 聚合。

| 报告区块 | SQL/逻辑 | 会员看到 |

| 连续观察 | `lifecycle=1` + 7 日趋势 | 观察池专题 |

### 5.3 商品数据字段对齐（核心）

> 本节只讲 **`premium_goods` 每一行商品字段**（销量、价格、粉丝、标题等）在云 PG 与本地 SQLite 之间如何合并。  
> **词包调度、catalog 对账** 见 §4.4 / §5.6，与商品字段合并无关。

#### 5.3.1 典型场景：同 goods_id 两端字段不一致

| 本地 SQLite | 云 PG | 商品字段怎么处理 |
|-------------|-------|------------------|
| `sold_num=1200`，今早 APP 扫 | `sold_num=1180`，昨/cloud 扫 | **本地胜**（`last_metric_scan` 更新） |
| `sold_num` 3 天未更新 | `sold_num` 今早 Agent 扫 | **云/Agent 胜**（本地 pull 写回） |
| `shop_fans=0` | `shop_fans=8500` | **采非零**（0 视为未采到） |
| `tier=A` | `tier=B` | **本地 tier 不变**（业务字段） |
| 本地无此行 | 云有完整行 | 整行 insert（§5.6 catalog），再走路径合并 |

本地每天扫 **一部分** 商品是常态：**未扫到的行保留旧快照**，等云/Agent 补扫后 **pull 更新扫描字段**，不要用旧本地快照覆盖云上的新数据。

#### 5.3.2 字段三分法

| 类别 | 商品字段 | 合并规则 |
|------|----------|----------|
| **① 扫描快照** | `sold_num`, `velocity_1d`, `actual_velocity_1d`, `deal_price`, `shop_fans`, `shop_sales`, `last_scan_status` | **最新可信扫描整组覆盖**（§5.3.3） |
| **② 派生** | `shop_fans_delta_1d`, `shop_fsr`, `goods_fsr`, `burst_score` | 用最新 ① 在本地 **重算** 后同步 |
| **③ 本地业务** | `primary_keyword`, `fallback_keywords`, `tier`, `scan_priority`, `monitor_freq` | **以本地为准**；云不得改 keyword/tier |
| **④ 档案** | `title`, `store_id`, `store_name`, `is_virtual` | 最新 **非空** 扫描覆盖 |
| **⑤ 溯源** | `last_metric_scan`, `last_app_scan`, `last_cloud_scan`, `last_agent_scan`, `scan_owner`, `last_scan_engine` | 分来源记录（§5.3.4） |

#### 5.3.3 扫描快照合并（每条 goods_id）

**可信度**（仅当 `last_metric_scan` 相同时比较）：`local_app > local_agent > cloud_api > cloud_web`

```
incoming.last_metric_scan > local.last_metric_scan  →  incoming 整组 ① 覆盖
incoming.last_metric_scan < local.last_metric_scan  →  保留 local，丢弃 incoming ①
相等  →  可信度高的 incoming 覆盖
```

**① 扫描快照整组字段**（一次扫描同时更新，禁止拆开拼）：

`sold_num`, `velocity_1d`, `actual_velocity_1d`, `deal_price`, `shop_fans`, `shop_sales`, `last_scan_status`, `last_scan_engine`, `scan_owner`, `last_metric_scan`

**特殊规则**：

- `sold_num` / `deal_price`：取 **最新观测值**，不取历史 max
- `shop_fans` / `shop_sales`：incoming `≤0` 时不覆盖已有非零值
- 覆盖后重算 ②：`shop_fsr`, `goods_fsr`, `shop_fans_delta_1d`（见 §4.5）

#### 5.3.4 溯源字段（判断「这条商品数据从哪来」）

| 字段 | 写入条件 |
|------|----------|
| `last_metric_scan` | 任意来源更新 ① 时写入 — **合并胜负手** |
| `last_app_scan` | 仅本地 APP 扫描 |
| `last_cloud_scan` | 仅云 gap/API 补扫 |
| `last_agent_scan` | 仅家里 Agent |

看商品数据是否新鲜 → 看 `last_metric_scan`，不是只看 `last_app_scan`。

#### 5.3.5 全字段 push / pull 对照

| 商品字段 | push | pull 写本地 | 冲突 |
|----------|------|------------|------|
| `sold_num`, `velocity_*`, `deal_price` | ✓ | ✓ | §5.3.3 |
| `shop_fans`, `shop_sales`, `shop_fans_delta_1d` | ✓ | ✓ | §5.3.3 + §4.5 |
| `shop_fsr`, `goods_fsr`, `burst_score` | ✓ | ✓ | 随 ① 重算 |
| `title`, `store_id`, `store_name` | ✓ | ✓ | 最新非空 |
| `primary_keyword`, `tier` | ✓ | **不覆盖** | 本地 |
| `lifecycle` | ✓ | 仅更严 | 归档>降频>观察>活跃 |
| `scan_priority`, `monitor_freq` | ✓ | 一般不 pull | 本地 |
| `last_*_scan`, `scan_owner` | ✓ | ✓ | §5.3.4 |

#### 5.3.6 权威分工（商品数据）

| 商品数据 | 听谁的 |
|----------|--------|
| 销量、价格、粉丝、扫描状态 | **`last_metric_scan` 最新的那次扫描** |
| 关键词、tier、调度 | **本地** |
| 会员报告展示 | **云 PG**（合并后的商品行镜像） |

### 5.4 商品字段同步时序

```
本地扫商品 → 写 SQLite ①⑤ → push 变化的 goods_id 行
云 upsert  → merge_scan_metrics(云行, incoming)；不改 ③ keyword/tier
云/Agent 补扫 → 更新云 ①⑤ → premium-changes 队列
本地 pull  → merge_scan_metrics(本地行, 云行)；不改 ③
```

**验收**（商品字段新鲜度，与词包无关）：

```sql
SELECT COUNT(*) FILTER (
         WHERE last_metric_scan > NOW() - INTERVAL '24 hours'
       ) * 100.0 / NULLIF(COUNT(*), 0) AS metric_fresh_pct
FROM premium_goods WHERE lifecycle < 3;
-- 目标 metric_fresh_pct > 95%
```

### 5.5 精品目录对账（与字段合并分开，§5.6）

`premium-catalog` 只解决 **云有本地无 / 本地有云无** 的 **行是否存在**，不解决同行字段冲突。字段冲突一律走 §5.3.3。

### 5.6 catalog 与 gap（补行 + 补扫，非字段规则）

**每日 catalog**（`POST /api/v1/sync/premium-catalog`）：

| 差异 | 动作 |
|------|------|
| `cloud_only` | 本地 insert 商品行（带云侧已有字段），后续走正常 push/pull 合并 |
| `local_only` | push 到云 |
| 双方都有但 `last_metric_scan` 均 >48h | 告警；由 gap 补扫刷新 ① |

**gap 补扫**（云 daemon / Agent）：只更新该 `goods_id` 的 ①⑤，本地靠 **pull** 对齐商品字段。

```sql
SELECT goods_id, title, primary_keyword, tier, scan_priority
```

## 12. 风险与对策

| 风险 | 对策 |
|------|------|
| primary_keyword 缺失导致 APP 无法扫 | ingest 后强制 `--resolve-keywords`；无词则 lifecycle=3 不入队 |
| 双写冲突 | §5.3.3 按商品扫描快照+时间戳合并 |
| 本地未扫全云侧精品 | 正常；catalog + gap 补扫 + pull 收敛，不追求 100% local_app |
| shop_fans 一端为 0 | 0 不覆盖非零；双端有值时取最新扫描 |
| 云仍被限流 | 云只扫 gap 小批；主扫必须在 APP |
| 采集机离线 | 云 gap 队列积压；恢复后 catalog 对账 |
| 词库版权/重复 | 核心词去重；L1 批内去重 |
| 迁移期双 daemon | feature flag `pool_cycle.mode=gap_only` 灰度 |
